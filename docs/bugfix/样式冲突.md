# 样式冲突（GeneratePress × Tailwind × 模块组件）

本文记录两类已发生的样式冲突：
- 段落不居中（排版/布局类冲突）
- Slider 按钮与 Dots 指示器被主题 button 样式干扰（组件类冲突）

并沉淀一套“常见干扰清单 + 排查方法 + 后续开发方式调整建议”，减少反复试错。

更新日期：2026-05-05

---

## 1) 案例复盘

### A. 段落不居中（实际：左对齐 / 未按设计居中）

**现象**
- 某些模块标题下方的说明段落，设计稿要求居中（容器居中 + 文本居中），但页面呈现为非预期（常见是文本左对齐或容器未居中）。

**典型根因**
- 主题对内容区（例如 `.entry-content p`）存在基础排版规则：`margin`、`max-width`、`text-align`、`line-height`、`display` 等。
- 当模块以“内容区默认标签”承载文案（直接使用 `p`，且上下文处于 `.entry-content`），主题可能通过更高优先级或更晚加载的样式覆盖 Tailwind 工具类。
- 真实案例（About 页面 Timeline / Team 标题区）：`text-align: center` 已命中，但 Tailwind 的 `mx-auto` 被主题覆盖为 `margin-left/right: 0`，导致 `h2/p` 作为 block 元素“贴左”，视觉上像没居中。

**修复策略（原则）**
- 以“模块容器”为边界做样式主权划分：模块内部排版（宽度、对齐、间距、颜色）由模块负责，避免依赖主题默认段落规则。
- 对于关键位置（标题/副标题），优先使用模块内的确定性布局（`max-w-* + mx-auto + text-center`），必要时使用更高权重的组件类覆盖主题。

**DevTools 定位要点（如何一眼看出是 margin 被盖掉）**
- Elements 选中目标 `h2/p`，看 Computed：
  - `text-align` 可能已经是 `center`
  - 但 `margin-left/right` 若仍为 `0px`（而不是 `auto` / 或者自动分配的数值），说明 `mx-auto` 未生效
- 再看 Layout/盒模型：元素 left 与父容器 left 相同，也能印证“block 没居中”

**修复策略（本次采用：组件类锁死 block 居中）**
- 在模块标题容器使用稳定类名（例如 `.lc-section-header`）
- 同时锁死“文本对齐 + block 居中”，避免 `mx-auto` 被覆盖：

```css
.lc-section-header,
.lc-section-header :where(h1, h2, h3, h4, h5, h6, p) {
  text-align: center !important;
}

body.lc-app #page .lc-section-header > :is(h1, h2, h3, h4, h5, h6, p) {
  margin-left: auto !important;
  margin-right: auto !important;
  margin-inline: auto !important;
}
```

### B. Slider 左右按钮 / Dots 指示器被主题样式干扰（实际：变成“主题按钮”）

**现象**
- 设计稿：左右切换按钮为正圆（`40×40`，圆形边框，hover 变蓝底白字）。
- 现场：按钮变成“胶囊长方形”，同时 dots 指示器出现“黑色长条/不按设计的按钮外观”。

**DevTools 定位结果（关键证据）**
- GeneratePress 命中以下规则（示例）：
  - `button, input[type="button"], input[type="reset"], input[type="submit"] { padding: 10px 20px; font-size: 17px; line-height: 1.5; appearance: button; ... }`
  - `body, button, input, select, textarea { font-family: ... }`
- 这些规则会把 slider 的按钮尺寸“撑大”，即使有 `border-radius: 9999px` 也只会变成更圆的胶囊，而不是正圆。

**修复策略（本次采用）**
- 对关键交互组件使用“强制重置 + 明确尺寸”，彻底摆脱主题对 button 的默认约束：
  - `button.slider-button`：固定 `width/height: 40px`，`padding: 0`，`font-size/line-height: 0`，`border-radius: 9999px`
  - `button.dots-indicator`：固定 `8×8`，激活态 `32×8`，同样重置 padding/font-size/line-height
- 同时保证 Tailwind 编译产物更新并被页面加载（`assets/css/style.css?ver=...` 发生变化）。

## 2) 常见“主题样式干扰”清单（高频）

### 2.1 Button / Link / Form（最高频）
- `button`、`input[type=submit]`、`a.button`：padding、background、border、text-transform、line-height、min-height
- `a`：颜色、下划线、hover
- `input/textarea/select`：border-radius、outline、box-shadow、font-size、line-height、padding

### 2.2 Typography（段落/标题）
- `p`：margin-bottom、line-height、max-width、text-align
- `h1-h6`：margin、font-weight、letter-spacing、text-transform
- `.entry-content *`：主题往往会在内容区加“阅读排版优化”，会影响模块组件

### 2.3 Layout（容器与栅格）
- `.container / .grid / .inside-article / .site-content` 等主题布局容器的 padding、max-width
- `img` / `figure`：display、margin、max-width: 100%
- `table`：border-collapse、font-size、padding

### 2.4 Lists / Media
- `ul/ol/li`：list-style、padding-left、margin
- `svg`：vertical-align、display

## 3) 排查方法（DevTools 工作流）

### 3.1 必做三步
1) Elements → 选中目标元素（例如按钮）  
2) Styles → 找到“最终生效规则”与被覆盖规则（看来源文件与 selector）  
3) Computed → 验证关键属性是否正确（width/height/padding/font-size/line-height/border-radius/background）

### 3.2 快速判断“是不是主题在干扰”
- 只要看到规则来源是 `.../themes/generatepress/...`，且 selector 包含 `button`、`.entry-content p`、`a.button`，基本可以直接判定“主题干预”。

### 3.3 关键指标（用来判断设计是否被破坏）
- 交互组件：`width/height/padding/line-height/font-size/border-radius`
- 排版模块：`max-width/margin-left/right/text-align/line-height`

## 4) 后续如何避免：开发方式是否需要调整？

结论：**需要做“样式主权划分”与“作用域隔离”，否则成本会持续上升。**

### 4.1 推荐的职责划分（各司其职）

**主题（GeneratePress + Child）负责：全局地基**
- 页面整体布局容器（header/footer/main 的结构与全局间距）
- 全局字体栈（`body`）、基础背景色、基础链接重置（已在 `@layer base` 做了部分）
- 少量通用的可复用组件类（例如 `.nav_tab` 这类“平台级组件”）

**模块（template-parts / blocks）负责：模块内部视觉与交互**
- 模块内的布局、排版、颜色、交互反馈（hover/active/disabled）
- 关键交互元素（按钮、dots、tabs）不依赖主题默认 `button` 样式

### 4.2 两条落地策略（建议选其一为主）

**策略 A（推荐）：模块作用域隔离（Scope First）**
- 每个模块最外层加一个稳定的 scope 类（例如 `lc-scope` / `copper-scope`）。
- 在 `src/input.css` 用 `@layer components` 写“只在 scope 内生效”的重置与组件样式，例如：
  - `.lc-scope button { ... }`
  - `.lc-scope p { ... }`
- 优点：不会污染全站，冲突可控；模块可维护性强。

**策略 B：关键元素强制“自成体系”（Component First）**
- 对高风险元素直接用组件类锁死（如 `button.slider-button`、`button.dots-indicator`），必要时用 `all: unset` 或强制尺寸/排版属性。
- 优点：最快、最稳定；缺点：如果滥用会导致“组件样式散落、复用困难”。

实践建议：**A 做底层隔离，B 用于少数精密交互控件（slider、tabs、cta）**。

### 4.3 什么时候应该“让主题控制”，什么时候“必须代码控制”

**让主题控制（降低成本）**
- 全局段落默认行高、正文色阶、链接默认行为（非模块内的富文本区域）
- 文章/页面内容区（Blog/Content Pages）的阅读体验

**必须代码控制（保证像素一致）**
- 任何“设计稿对齐”的模块区块（产品页、首页模块、定制卡片、slider/tabs）
- 交互组件（按钮、指示器、卡片 hover、表单控件）
- 技术数据排版（`font-mono` 的表格/合金牌号/尺寸参数等）

### 4.4 用“小白能懂”的类比解释：为什么要给每个模块套一个 scope？

下面这段用完全不懂代码的人也能理解的方式解释：

#### 类比 1：主题是“整栋楼的物业统一装修”，模块是“你房间里的精装修”

- **主题（GeneratePress）**就像物业：它会给整栋楼定一套统一规则，比如
  - 所有门把手（button）默认都要多宽、配什么颜色
  - 所有墙上的段落（p）默认行距多少、下边距多少
- **模块**就像你自己的房间：你要做的是“完全按设计稿精装修”，每个柜子、每个灯的尺寸都要精准。

问题出在：物业的统一规则是“全楼生效”的。你房间里刚装好的圆形按钮，物业突然说“门把手统一要带 10px 20px 的把手护套（padding）”，结果按钮立刻被撑成胶囊形。

#### 类比 2：scope 就是“在房间门口贴一张施工牌：房间内按设计图施工，外面按物业规则”

给模块最外层套一个 scope 类（例如 `.lc-scope`），等价于：
- “**这间房间里**，不要套用物业默认的门把手/段落规则”
- “这间房间里由**我们的设计图（Tailwind + 组件类）**说了算”

这样你就不用每次都在现场（页面）和物业争论：
- 为什么这个按钮又变大了
- 为什么段落又不居中了

你只要保证：进入 scope 的房间，按一套确定的施工标准走，视觉就稳定。

#### 这套做法的优点（为什么能省心）

- **减少冲突**：主题的 `button/p/a` 默认样式不再到处“干预模块”
- **更可预期**：模块内部样式只由模块决定，改动范围清晰
- **排查更快**：UI 不对时优先看“scope 内规则”，不会在全站规则里迷路

#### 这套做法的缺点（提前知道，避免踩坑）

- **需要一份“房间内的基础装修标准”**：scope 里按钮、段落、列表、表单默认长什么样，需要你定义一次（否则每个模块都要手动补很多类）。
- **可能导致“重复装修”**：如果每个模块都各写一份 reset，会造成 CSS 体积变大。更好的方式是：用一份统一 `.lc-scope` 基线，模块只写差异。
- **第三方内容可能变“太素”**：有些插件/富文本原本依赖主题默认样式，放进 scope 后需要你在 scope 内补上对应的样式。

#### 推荐落地方式（不折腾版）

1) 全站统一一个 scope 基类：例如 `.lc-scope`  
2) 在 `src/input.css` 写一份“只在 `.lc-scope` 内生效”的基础规则，优先覆盖高冲突项：`button / a / p / ul/ol / input`  
3) 少数精密交互控件继续用组件类锁死（例如 `button.slider-button`、`button.dots-indicator`），确保像素一致

## 5) 建议的“防冲突基建”清单（可逐步实施）

1) 统一模块容器：每个主模块都使用 `max-w-[1280px] mx-auto`，并遵循垂直节奏（`pt-[px]`）  
2) 引入模块 scope：`<section class="lc-scope ...">`，逐步把排版重置放进 scope 内  
3) 对 button/form 建立平台级组件类：`slider-button`、`dots-indicator`、`btn-primary` 等，禁止裸用 `button` 依赖主题  
4) 把“冲突高发点”做成检查清单：每次 UI 不对先看 `Computed` 的 `padding/font-size/line-height`

## 6) 对本项目的现实评估

当前栈（GeneratePress + Tailwind + Alpine + ACF）在“模块式开发”上是成立的，但前提是：
- **明确：主题是地基，不是装修师傅**
- **模块必须拥有样式主权**

如果不做 scope 与组件化，开发会进入“不断和主题抢样式”的状态，时间会被吞掉；DevTools 可以把问题定位得很快，但更重要的是让问题“少发生”。
